# File organization

The goal is small files with one reason to change. Size limits are enforced by SwiftLint; hitting a
limit is a signal to split by responsibility, never a reason to disable the rule.

## Size limits (SwiftLint)

| Rule | Warning | Error (fails CI) |
|---|---|---|
| File length (excluding comments and blank lines) | 250 | 300 |
| Type body length | 150 | 200 |
| Function body length | 30 | 40 |
| Cyclomatic complexity per function | 8 | 12 |
| Function parameters | 5 | 7 |
| Nesting depth (types) | 1 | 2 |
| Line length | 120 | 140 |
| Large tuple | 2 | 3 |

CI runs `swiftlint --strict`, so warnings fail CI too. The two columns tell you how close you are.

`swiftlint:disable` is allowed only for a single line or the next line
(`// swiftlint:disable:next rule_name - reason`) with a reason. File-wide or block disables are not
accepted in review.

## One primary type per file

- Each file declares one primary type. Small private helpers used only by that type may live in the
  same file, below it.
- Protocol conformances may live in `Type+Protocol.swift` when they are more than a few lines.
- Enum cases with associated logic that grow large are split into extensions per concern, not into
  one giant `switch`.

## Inside a file

Order:

1. `import` statements, sorted, one per line, only what the file uses.
2. The primary type:
   1. Nested types
   2. Static properties
   3. Instance properties (stored, then computed)
   4. Initializers
   5. Public/internal methods
   6. Private methods
3. Extensions of the primary type (conformances), each preceded by `// MARK: - ProtocolName`.
4. File-private helpers.

Use `// MARK: -` to separate these groups only when the file has more than one group worth
navigating to.

## Inside a module

```
Sources/SnapboltUpload/
├── S3Uploader.swift                # the type other modules use
├── Signing/
│   ├── SigV4Signer.swift
│   └── CanonicalRequest.swift
├── Requests/
│   ├── ObjectRequest.swift
│   └── S3ErrorResponse.swift
└── ConnectionTest/
    └── ConnectionTester.swift
```

- The type(s) other modules use live at the module root; implementation details live in feature
  folders.
- A folder with more than ~8 files is a sign that a sub-responsibility should be its own folder or
  module.
- No `Models/`, `Extensions/`, `Protocols/`, `Utils/` folders (see [naming.md](naming.md#banned-names)).

## Splitting checklist

When a file or type is too big, ask in order:

1. Does it do more than one job? Extract each job into its own type.
2. Is there a pure calculation inside? Extract a pure function or value type — it also becomes
   testable.
3. Is it a long `switch` over cases? Give each case its own type behind a protocol, or move
   per-case logic into extensions.
4. Is it a view? Extract subviews.

## Generated and vendored files

- `*.xcodeproj` is generated by XcodeGen and not committed.
- No vendored third-party source. Dependencies come through SwiftPM
  ([ADR 0006](../adr/0006-dependency-policy-and-keyboardshortcuts.md)).
